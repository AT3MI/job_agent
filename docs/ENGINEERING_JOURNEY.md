# Инженерная история проекта

Как задача «генерировать сопроводительное письмо под вакансию» превратилась в систему
с контрактом, валидацией и детерминированными гарантиями. Каждый шаг ниже — реакция на
конкретный наблюдаемый дефект, а не заранее спроектированная архитектура.

## С чего начали

Задача была не «написать письмо», а **стабильно** генерировать сопроводительные под вакансию
с памятью и контекстом, локально и без американских сервисов. Первый подход — «промпт +
локальная модель»: Ollama, Chroma, затем GigaChat. От «просто чата» путь привёл к
структурированному пайплайну с контрактом и валидацией.

## Этапы

### 1. «Просто чат» не работает

Один большой промпт. Модель то писала хорошо, то «плыла»: копировала чужие факты из пар
писем, добавляла лишние блоки, путала структуру. Вывод: **промпт — не контракт**, стабильности
из текста инструкции не добиться.

### 2. Данные отделены от логики

Резюме, пары писем, факты вынесены в `data/`. Список фактов перестали вести руками:
`extract_facts.py` автоматически извлекает `technical_skills`, `soft_skills`, `projects`,
`education` из резюме через Structured Output (Pydantic-схема). Первый инженерный слой:
добавление факта — правка резюме + переиндексация, код не трогается.

### 3. Контракт выхода (Structured Output)

Вместо «напиши письмо» — JSON-схема `StandardOutput`: `intro`, `vacancy_interest`,
`best_solution`, `unique_block`, `projects`, `medtech_experience`, `why_you`, `closing`.
Модель физически не может добавить лишний блок — схема не позволяет. «Самодеятельность»
модели убрана.

### 4. Валидация стала программной

`deterministic.py` проверяет инварианты: `unique_block` начинается с «По … — отдельно»,
`closing` содержит контакты и ровно один формат работы, `why_you` не пересказывает вакансию.
Ошибки ловятся кодом, а не «на глаз»; при ошибках — retry конкретных полей.

### 5. Детерминизация там, где можно посчитать без LLM

Формат работы (closing) и маркер «— отдельно» (unique_block) перестали доверять модели:
Python сам определяет формат из текста вакансии (`detect_work_format`) и сам гарантирует
канонический заголовок (`ensure_unique_block_format` — идемпотентный). Модель только
вставляет готовое. Retry для этих полей исчез.

### 6. Генерация и сборка разделены

Модель генерирует структуру (`StandardOutput`), Python собирает текст (`assemble_letter`):
проекты разворачиваются в читаемые блоки кодом, а не моделью. Ответственность разделена:
LLM — содержание, Python — форма.

### 7. Контракт расширен осознанно

Выяснилось, что потерялись значимые блоки: «Почему эта вакансия», «Лучшее решение», медтех,
личные качества. Добавлены в схему — не «подгонка», а осознанное расширение контракта под
реальную структуру хороших писем.

### 8. Утверждённое закреплено

Отшлифованный блок личных качеств модель переформулировать не должна: он вырезается из
резюме по маркеру и вставляется в письмо **дословно**, минуя модель. Формулировки, которые
утверждены, код не трогает.

### 9. Слой-лингвист поверх письма

Структура и факты стабилизировались, но вылезли поверхностные дефекты формулировок:
повторы фраз между соседними предложениями, тавтологии «проблема ↔ результат» в проектах,
грамматические обрывки. Ключевое ограничение: факты и структура зажаты сознательно — это
продуктовое требование, а значит источник ошибок — только язык. Решение: отдельный слой
корректора **поверх** готового письма, а не правка основного промпта.

Принцип слоя: **в коде нет лингвистических правил** — вся оценка качества на стороне модели;
код гарантирует механизм. Модель возвращает закрытый список дефектов с дословным `quote`
и `fixed` (полное исправленное предложение); код применяет правку хирургически: ищет quote
посимвольно, меняет ровно одно вхождение, проверяет инварианты (числа не терять, ссылки/
контакты не добавлять, длина ограничена, зачины заморожены). Любой сбой API — письмо без
изменений: слой never-fail.

### 10. Сжатие вызовов и механические стоп-краны

Первый живой прогон слоя: 3 вызова на письмо (генерация + проверка + верификация), ~9k
токенов. Часть правок верификатор ловил, но система была перегружена вызовами. Верификацию
заменили бесплатными механизмами: инварианты применения, повторная структурная валидация и
снапшот-откат; старый verify сохранён за флагом `VERIFY_LINGUIST=1`. Итог — **2 вызова на
письмо**. Дополнительно введён trigram-guard: правка не может дублировать 3+ подряд слов из
другого предложения того же поля («запихивание» повтора на новое место) — защита данных в
ряду «числа не терять», а не лингвистическое правило.

### 11. Правило зачинов

Конфликты «зачин ↔ обычное предложение» решаются правкой обычного предложения: зачин
(первое предложение абзаца) не переписывается, заголовок `unique_block` заморожен полностью.
Исключение — грамматический обрывок внутри зачина, который иначе неисправим: правится
минимально, остальное сохраняется посимвольно.

## Что получилось

- вход: `job.txt`, `resume.txt`, `allowed_facts.json` (генерируется автоматически);
- генерация: 1 вызов GigaChat с JSON-схемой; лингвист: +1 вызов;
- валидация: программные инварианты + детерминированные гарантии closing/unique_block;
- слой-лингвист: check → хирургические правки с инвариантами и guard → метаданные;
- сборка: Python склеивает письмо, проекты разворачиваются кодом;
- учёт: токены и вызовы логируются на каждом шаге;
- расширяемость: новый факт — правка резюме + переиндексация, код не меняется.

Это не «идеальный промпт», а система с контрактом, валидацией и детерминированными
гарантиями: модель ошибается — Python ловит, ограничивает или откатывает.
